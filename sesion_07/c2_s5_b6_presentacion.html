SESION 2.5 - EXPLAIN
El diagnostico mas util

Estimado contra real

Parallel Seq Scan on transacciones_volumen
    (cost=0.00..31287.33 rows=634 width=6)
    (actual time=1.692..157.210 rows=541 loops=3)
costCosto estimado, en unidades arbitrarias. No son milisegundos
rows=634Filas que el motor estima
actual timeMilisegundos reales de inicio y de fin
rows=541 loops=3Filas reales por vuelta, y numero de vueltas
Comparar el rows estimado contra el real es el primer diagnostico. Una diferencia de un orden de magnitud indica estadisticas desactualizadas o un predicado que el motor no supo estimar.
Con loops mayor que uno, rows es por vuelta. El total es el producto.
SESION 2.5 - PLANES
El efecto del indice

La misma consulta, dos planes

SELECT COUNT(*), SUM(monto) FROM pagos.transacciones_volumen
WHERE id_tarjeta = 42 AND fecha_hora BETWEEN '2026-03-01' AND '2026-03-31';
RecorridoTiempo
Sin indiceParallel Seq Scan166 ms
Con indice compuestoBitmap Index Scan9 ms
CREATE INDEX idx_tarjeta_fecha
    ON pagos.transacciones_volumen (id_tarjeta, fecha_hora);
Orden de las columnas: las de igualdad primero, la de rango al final. Aqui id_tarjeta filtra por igualdad y es muy selectivo, 219 valores sobre dos millones de filas.

El indice cuesta espacio y escritura

MedicionResultado

500 mil inserciones sin indices0.8 s

Cada indice se actualiza en cada insercion, actualizacion y borrado. Con tres indices, cada fila implica cuatro escrituras.
Un indice que no se usa no es neutro: paga espacio y paga escritura sin devolver nada.

SESION 2.5 - DIAGNOSTICO
Caso mas util

Una funcion sobre la columna inutiliza el indice

-- Seq Scan, 191 ms
WHERE DATE(fecha_hora) = '2026-03-15'

-- Index Only Scan, 27 ms
WHERE fecha_hora >= '2026-03-15' AND fecha_hora < '2026-03-16'
El indice esta sobre fecha_hora. La expresion DATE(fecha_hora) es otro valor, que no esta almacenado en ninguna parte.
Es el mismo fenomeno de la sesion 2.4 con ->>: el indice cubre la columna, no las expresiones aplicadas sobre ella.
Dos correcciones: reescribir como rango, o crear un indice de expresion sobre DATE(fecha_hora).
SESION 2.5 - DIAGNOSTICO
Otros tipos de indice

Parcial y de cobertura

-- Parcial: solo indexa las filas que cumplen la condicion
CREATE INDEX idx_rechazadas ON pagos.transacciones_volumen (id_tarjeta)
    WHERE estatus = 'RECHAZADA';

-- De cobertura: la consulta se resuelve sin visitar la tabla
CREATE INDEX idx_cobertura ON pagos.transacciones_volumen
    (id_tarjeta, fecha_hora) INCLUDE (monto);
VACUUM ANALYZE pagos.transacciones_volumen;
VACUUM, no solo ANALYZE. El Index Only Scan requiere el mapa de visibilidad actualizado. Sin el, el plan degrada a Bitmap Heap Scan aunque el indice tenga todas las columnas.
El contador Heap Fetches del plan debe ser cero.
SESION 2.5 - INDICES
Criterio

Cuando crear un indice

FactorFavorece crearlo
FrecuenciaLa consulta corre miles de veces al dia
SelectividadEl filtro devuelve una fraccion pequena de la tabla
EscrituraLa tabla se lee mucho mas de lo que se escribe
EspacioHay margen en disco y en memoria compartida
Formulacion breve: se indexa lo que se consulta con frecuencia y devuelve poco. Todo lo demas se evalua con el plan antes de decidir.
pg_stat_user_indexes revela los indices que nunca se usan. Con la salvedad de que el contador arranca en el ultimo reinicio de estadisticas: un indice del cierre mensual puede aparecer en cero un martes cualquiera.

SESION 2.5 - TRANSACCIONES
Desde Python

psycopg no confirma solo

with psycopg.connect(cadena()) as conexion:
    conexion.execute("UPDATE pagos.saldos SET saldo = saldo - 300 WHERE id = 1")
    conexion.execute("UPDATE pagos.saldos SET saldo = saldo + 300 WHERE id = 2")
# al salir sin excepcion: COMMIT.  con excepcion: ROLLBACK.
Fuera del bloque with, la transaccion queda abierta hasta que se llame a commit() o a rollback(). El error clasico es insertar, cerrar el programa y no encontrar el dato.
La restriccion vive en la tabla, no en Python. Verificar el saldo en el codigo deja una ventana entre la lectura y la escritura.
SESION 2.5 - TRANSACCIONES
Un error que confunde

La conexion deja de responder

psycopg.errors.UndefinedTable: relation "no_existe" does not exist
psycopg.errors.InFailedSqlTransaction: current transaction is aborted,
    commands ignored until end of transaction block
Tras un error, PostgreSQL marca la transaccion como abortada y rechaza todo hasta que se revierta. El segundo mensaje no dice nada sobre la causa real.
Dos soluciones: rollback() dentro del bloque except, o un punto de guardado antes de la sentencia que puede fallar.
SESION 2.5 - ERRORES
Puntos de guardado

Perder un registro sin perder el lote

for registro in lote:
    try:
        with conexion.transaction():        # crea un SAVEPOINT
            conexion.execute("INSERT INTO ... VALUES (%s, %s)", registro)
        guardados += 1
    except psycopg.Error:
        descartados += 1
El bloque anidado revierte solo su parte. Sin el, el primer error aborta la transaccion completa y se pierde todo lo insertado antes.
Es el patron de una carga por lotes en la que algunos registros vienen mal y no se quiere detener el proceso.

SESION 2.5 - ERRORES
Medicion

Un solo cronometraje no dice gran cosa

  • La primera ejecucion lee de disco; las siguientes, de memoria
  • El equipo ejecuta otros procesos que compiten por recursos
  • El planificador puede elegir planes distintos segun las estadisticas
Procedimiento defendible: una ejecucion de calentamiento sin medir, cinco repeticiones, reportar el minimo, y declarar cuantas repeticiones y que estadistico se uso.
El tiempo dice cuanto tardo. El plan dice por que. Una medicion sin plan es la mitad del diagnostico.
