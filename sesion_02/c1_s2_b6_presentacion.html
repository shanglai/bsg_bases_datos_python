Tres niveles de modelado

NivelPregunta que respondeProducto
ConceptualQue cosas existen en el negocio y como se relacionanDiagrama de entidades y cardinalidades
LogicoQue atributos tiene cada entidad y que la identificaAtributos, llaves primarias y foraneas
FisicoComo se implementa en un motor concretoArchivo DDL con tipos y restricciones
El nivel conceptual es independiente del motor. El nivel fisico cambia entre SQLite, PostgreSQL y cualquier otro motor relacional. Esa separacion permite reutilizar el trabajo de modelado cuando cambia la tecnologia.
El error frecuente consiste en iniciar por el nivel fisico, escribiendo tablas antes de haber decidido que entidades existen.

Criterio de descomposicion

Las tres primeras formas normales

FormaReglaCaso en el archivo plano
PrimeraCada celda contiene un solo valorSe cumple: el extracto ya es atomico
SegundaNingun atributo depende de parte de la llaveLa ciudad depende del comercio, no de la transaccion
TerceraNingun atributo depende de otro atributo no llaveLa categoria depende del comercio, no de la operacion
El resultado practico de aplicarlas es que cada dato reside en un solo lugar. El correo de un cliente deja de repetirse en cada una de sus operaciones.
Consecuencia directa: corregir un dato pasa de modificar cientos de filas a modificar una sola.

SESION 1.2 - LOGICO
Nivel fisico

La restriccion que resuelve el problema

CREATE TABLE comercios (
    id_comercio INTEGER PRIMARY KEY,
    nombre      TEXT NOT NULL UNIQUE,
    categoria   TEXT NOT NULL,
    ciudad      TEXT NOT NULL
);
UNIQUE sobre el nombre es lo que impide que reaparezcan las diecisiete variantes de escritura. La regla queda declarada en la estructura y el motor la aplica en toda escritura, venga de donde venga.
Una funcion de limpieza en el codigo de carga resuelve el caso presente. Una variante de escritura nueva volveria a producir duplicados, porque esa funcion solo actua durante la carga.
SESION 1.2 - DDL
Nivel fisico

Llave compuesta y llave foranea

CREATE TABLE terminales (
    id_terminal INTEGER PRIMARY KEY,
    id_comercio INTEGER NOT NULL,
    codigo      TEXT NOT NULL,
    UNIQUE (id_comercio, codigo),
    FOREIGN KEY (id_comercio) REFERENCES comercios (id_comercio)
);
UNIQUE (id_comercio, codigo) declara que el codigo es unico dentro del comercio. FOREIGN KEY impide registrar una terminal de un comercio que no existe.
En SQLite, las llaves foraneas no se aplican de forma predeterminada. PRAGMA foreign_keys = ON debe emitirse en cada conexion.
SESION 1.2 - DDL
Nivel fisico

Restricciones de dominio

CREATE TABLE transacciones (
    id_transaccion TEXT PRIMARY KEY,
    fecha_hora     TEXT NOT NULL,
    id_terminal    INTEGER NOT NULL,
    id_tarjeta     INTEGER NOT NULL,
    monto          REAL NOT NULL CHECK (monto > 0),
    moneda         TEXT NOT NULL DEFAULT 'MXN',
    estatus        TEXT NOT NULL
                   CHECK (estatus IN ('APROBADA','RECHAZADA','REVERSADA')),
    FOREIGN KEY (id_terminal) REFERENCES terminales (id_terminal),
    FOREIGN KEY (id_tarjeta)  REFERENCES tarjetas (id_tarjeta)
);
CHECK limita el conjunto de valores admitidos. Un estatus mal escrito deja de ser posible, sin que ninguna aplicacion tenga que validarlo.
