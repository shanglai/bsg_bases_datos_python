SESION 2.4 - OPERADORES
La confusion mas frecuente

Una flecha o dos

autorizacion->'emisor'->'nombre'    -- jsonb:  "BANORTE"  con comillas
autorizacion->'emisor'->>'nombre'   -- text:   BANORTE    sin comillas
Regla de uso: -> en los pasos intermedios, ->> en el ultimo. 
SELECT '9' > '90'  AS comparacion_de_texto;    -- verdadero
SELECT  9  >  90   AS comparacion_numerica;    -- falso
->> devuelve texto. Comparar un puntaje sin convertir a entero produce una comparacion alfabetica que no falla y da un resultado incorrecto.

SESION 2.4 - INDICES
Lo que se cede

El documento no valida nada

-- El modelo relacional rechaza esto
INSERT INTO pagos.transacciones (..., estatus, ...) VALUES (..., 'PENDIENTE', ...);
   ERROR: violates check constraint

-- El documento acepta cualquier cosa
SELECT '{"puntaje": "no es un numero",
         "senales": "tampoco es un arreglo"}'::jsonb;
   OK
JSONB valida que el documento sea JSON bien formado. Nada mas. No hay tipos, ni campos obligatorios, ni dominios.
Se recupera parte del control con CHECK sobre la columna o con columnas generadas, pero solo lo que se declare de forma explicita.
SESION 2.4 - LA CONTRAPARTIDA
Criterio

Que va en columna y que en documento

En columna

  • Existe en todas las filas
  • Participa en llaves o relaciones
  • Se filtra o se agrupa con frecuencia
  • Su ausencia debe rechazarse

En documento

  • La estructura varia entre filas
  • Los campos cambian sin previo aviso
  • Se lee casi siempre completo
  • Viene de un sistema cuyo formato no se controla
Regla breve: columna para lo que el modelo garantiza, documento para lo que el modelo no puede prever.

SESION 2.4 - SQLALCHEMY
JSONB desde el mapeo

El filtro debe ocurrir en el motor

# Acceso por operador, se traduce a ->>
select(func.count()).select_from(Transaccion).where(
    Transaccion.autorizacion["emisor"]["nombre"].astext == "BANORTE")

# Contencion, que puede usar el indice GIN
select(func.count()).select_from(Transaccion).where(
    Transaccion.autorizacion.contains({"captura": {"aplicacion": "CoDi"}}))
Traer las filas y filtrarlas con un ciclo de Python devuelve el resultado correcto, mueve cinco mil documentos por la red y deshace todo el trabajo de indexacion.
SESION 2.4 - SQLALCHEMY
El costo oculto del mapeo

Una consulta por cada acceso

# 7 comercios  ->  8 consultas
for comercio in sesion.execute(select(Comercio)).scalars():
    len(comercio.terminales)

# 7 comercios  ->  2 consultas
sesion.execute(select(Comercio).options(selectinload(Comercio.terminales)))
Con siete comercios la diferencia es irrelevante. Con siete mil, son siete mil consultas contra dos.
El patron no produce ningun error: solo se vuelve lento al crecer. Es el argumento principal para conocer que SQL genera el mapeo.
SESION 2.4 - MAPEO
Mapeo o SQL directo

Conviven, y esa convivencia es lo normal

Conviene el mapeoConviene el SQL directo
La unidad de trabajo es una entidad que se lee, se modifica y se guardaLa consulta es analitica: agregaciones, ventanas, CTE
Muchas operaciones parecidas sobre las mismas entidadesEl resultado no corresponde con ninguna entidad del modelo
Importa la portabilidad entre motoresSe usan caracteristicas propias del motor, como JSONB o GIN
El error no es elegir uno u otro, sino usar el mapeo para consultas analiticas sin saber que SQL genera.
SESION 2.4 - CRITERIO
Cierre

Lo que queda planteado

  • El documento resuelve la variabilidad que las columnas no absorben
  • Los operadores de busqueda usan el indice; el acceso comparado, no
  • Un indice existente no garantiza que se use
  • Se cede la garantia de estructura, y solo se recupera lo que se declare
Pregunta que abre el capitulo 3: si esta es la ventaja del modelo documental, y PostgreSQL ya almacena, indexa y consulta documentos, que aporta MongoDB por encima de lo que se vio hoy.
